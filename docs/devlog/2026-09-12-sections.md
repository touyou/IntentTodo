# カテゴリ配下のセクションを実装し `.reminders.section` / `createSection` に適合した件（#139）

[同日の Intent スキーマ適合](2026-09-12-intent-schema-adoption.md)で `createReminder` の要求に
`section: SectionEntity?` が含まれていることが分かった。スタブで型だけ用意する案も出たが、
**メタデータで「セクションを持つアプリ」と名乗るなら実体を持つ**ことにして、モデルから
UI まで通した。

## 1. 途中で分かった前提: カテゴリを付ける経路が無かった

セクションの前にリストが要る、という順で見ていて気づいた。**`Category` は entity / スキーマ
（`.reminders.list`）として公開されているのに、todo に付ける書き込み経路がどこにも無かった**
（`TodoService` で `item.category` を書くのは undo の復元だけ、`AddTodoIntent` に list パラメータ
無し、UI にもピッカー無し）。読み取り専用の関連が entity には出ている状態だった。

そのため、このコミットは 2 つを同時に足している:

- `list`（カテゴリ）の書き込み経路 — `createReminder` の `list` 要求にもそのまま乗る
- `section` — 新しい `TodoSection` モデル + `.reminders.section` 適合

## 2. モデル

```
Category ──(cascade)── TodoSection ──(nullify)── TodoItem
```

- `Category.sections` 側に `@Relationship(deleteRule: .cascade, inverse: \TodoSection.category)`
  を置いた（`TodoItem.subTasks` と同じ「親側で cascade」の形）。セクションはカテゴリの外では
  意味を持たず、`.reminders.section` が `list` を**非 optional**で要求するため
- `TodoSection.todos` は nullify。セクションを消しても todo は残り、配属だけ外れる
- CloudKit 要件どおり属性は全部デフォルト値つき、関連は全部 optional
- `TodoItemSnapshot` に `sectionID` を足した。undo が配属まで戻さないと、削除 → 復元で
  静かにセクションから消える

## 3. 配属のルールは 1 か所（`TodoService.applyFiling`）

list と section は食い違いうる（別リストのセクションを指定できる）。決めた規則:

| 入力 | 結果 |
|---|---|
| section を指定 | section を付け、**その section の list も一緒に付く**（section が勝つ） |
| list を別のものに変更 | その list に属さない section は外れる |
| list を明示的に nil | list も section も外れる |
| 解決できない id | `throw`（無音で「どこにも配属されていない」になるのを避ける） |

Siri / Shortcuts から来る値と UI から来る値の両方がここを通る。UI 側のピッカーも同じ規則で
連動させた（セクションを選ぶとリストが追随、リストを変えるとセクションが外れる）ので、
**フォームからは Intent が拒否する配属を作れない**。

## 4. 適合の実測

- `TodoSectionAppEntity` を `@AppEntity(schema: .reminders.section)` に適合。要求は `name` +
  `list`（非 optional）で、`TodoItem.category` と同じ理由（CloudKit）で model 側は optional な
  ため、カテゴリを失ったセクションは `CategoryAppEntity.uncategorized` の下に見せる
- **watch には別型名**（`WatchTodoSectionAppEntity` + `typealias`）。`AddTodoIntent` /
  `UpdateTodoIntent` がパラメータとして持つので型自体は両プラットフォームに必要で、
  型名を共有すると iOS の統合メタデータが watch スライスに上書きされる（FB24570185）
- `CreateSectionIntent` を `@AppIntent(schema: .reminders.createSection)` に適合。
  要求は `name: String` + `list: ListEntity` → `ReturnsValue<SectionEntity>` で、
  **初回ビルドで診断ゼロ**（要求を外して測る手間が要らなかった唯一の例）

iOS 27.0 Simulator のクリーンビルド（`/tmp/ITSchemaProbeDD`）で確認:

```
CreateSectionIntent  [{'domain': 'reminders', 'name': 'CreateSectionIntent'}]
TodoSectionAppEntity [{'domain': 'reminders', 'name': 'SectionEntity'}]
```

既存 4 本（`OpenTodoIntent` / `OpenCategoryIntent` / `DeleteTodosIntent` /
`ShowTodoSearchResultsIntent`）と 3 entity の schema も残っており、SSU エラー 0 件 /
`nlu.appintents` 生成あり。

## 5. テスト

`TodoFilingTests`（11 本）で配属規則・`createSection`・undo 復元を固定した。関連は
出荷メタデータにも UI にも現れない位置にあるので、ビルドが緑でも規則が壊れても気づけない。

- パッケージ: 159 tests passed（TodoAppIntents）/ 30（Repository）/ 19（Domain、App Group の
  既知 issue 1 件）
- `IntentTodoUITest` の AppIntents 3 スイート 23 tests passed

## 6. 残り

`reminders` ドメインで未適合なのは `createReminder` / `updateReminder`（#138）と
`createList` / `reminders.group`（#139）。`createReminder` は `section` 要求を満たせるように
なったので、残るのは `images`（添付）とパラメータのリネーム / 型変更。
