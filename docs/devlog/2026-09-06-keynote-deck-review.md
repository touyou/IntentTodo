# 2026-09-06 Keynote の実物をレビューできるようにした

登壇スライド（`iosdc2026_appintents_centric.key` / 118 面）は iCloud Drive にあり、これまで
**中身をレビューできていなかった**。`docs/presentation/` にあるのは骨子と原稿（`99-script.md`）だけで、
**実際に投影されるものは誰も突き合わせていない**状態だった。今回そこを読める形にして、原稿レビュー
（[99-script.notes.md](../presentation/99-script.notes.md)）の決定が実物に入っているかを確認した。

結果は [99-keynote.notes.md](../presentation/99-keynote.notes.md)。ここには経緯と、途中で間違えたことを残す。

## 1. `.key` は protobuf なので、AppleScript で 2 つ吸い出した

`.key` はディレクトリパッケージで、本文は `Index.zip` の中の IWA（protobuf）。テキストとして
grep できない。Keynote が起動していれば AppleScript が使えるので、

1. **PDF 書き出し** → 版面をページ画像として読む
2. **`text items` + `presenter notes` の全面ダンプ** → 文言と喋る内容をテキストで読む

の 2 経路にした。手順は 99-keynote.notes.md の F にまとめた。ダンプで詰まったのは 2 点:

- `default title item` / `default body item` は**このテンプレートでは常に空**。
  マスター由来ではなく自由配置のテキストボックスなので、**`text items` を回さないと何も取れない**
- `export ... with properties {skipped slides:false}` を書くとき、
  AppleScript 側のローカル変数名に `skipped` を使うと `-10006`（「skipped を false に設定できません」）で
  落ちる。予約語衝突。変数名を変えれば通る

**Keynote には第 2 部相当が `S91`–`S118` として既に入っていた**（つまづき 3 本 / donation の答え合わせ /

（原稿は直接編集しない運用のため、原稿側は追従させない）。

## 4. 尺の見積もりを 2 回間違えた

1. **1 回目（このセッションの最初）**: 発表者ノート 10,811 字を **330 字/分**で割って「33〜39 分。
   40 分枠の余白はゼロ」と書き、歴史パートの圧縮を提案した。→ **本人の通し実測が 34 分 28 秒**で、
   余白が 5.5 分あることが判明。提案は取り下げた
2. **前提の取り違え**: `99-script.notes.md` A-1 には **496 字/分**の実測（原稿の音読）が既にあったのに、
   一般値の 330 を使っていた。そして実際の通しは **314 字/分**だった

**素読みの話速（496）と本番の実効話速（314）は別物**で、後者はノートどおりに喋らないぶん
（間・言い換え・スライドを見せる時間）を含む。**原稿の字数から尺を出すなら 314 を使う**。
教訓としては、**尺は推定せず通しを計る**のが正しく、推定するなら**どちらの話速か**を明示する。

## 7. ⭐ D-1 は主張の構図を読み違えていた

`S45`–`S56` を「**透明化したから、その役割が App Intents に移る**」という因果として読み、
「透明化は視覚的な存在感の話で機能の移譲ではない」＝飛躍がある、と指摘した。実際の意図は違った:

> コンテンツ重視なのは分かるけど、それだけだと**アクセシビリティを下げてまでやった意味が分からない**。
> でも、もし**それを下げてもいい保険があるなら理念を追い求めることができる** →
> **App Intents はその保険のひとつになっていた**

つまり「理念 → 代償 → 代償を許せる保険があった」という構図で、**「なぜ Apple はそこまでやれたのか」の
説明**。飛躍ではない。D-2（`S54`）と D-3（AX 批判の扱い）も同じ意図から出ている表現だったので、
個別に言い直しを提案するのは構図を壊す方向だった。

**「保険」という語はスライドにもノートにも出てこない**ので、原稿を読まずに通した 1 人（このレビュー）は
誤読した。ただし会場では話し方と流れで補える範囲、という本人の判断。**観測だけ残して変更は求めない**形にした。

教訓: **登壇資料の「論理の飛躍」を指摘する前に、その順序に意図がある可能性を先に潰す**。
スライドとノートだけからは構図が復元できないことがある。

## 8. E-4 は指摘そのものが間違っていた

`S41`（これまで / 2026 年の対比表）について 2 点指摘したが、**両方成立していなかった**。

1. 「年号が**上 3 行**にだけ付いていて下 2 行に無い（不統一）」→ 年号が付いているのは **5 行中 2 行**。
   **行数を数えていなかった**。しかも付いている 2 行は「その年に導入された API」で、付いていない 3 行は
   **API ではなく当時の状態の記述**。年号が要るのは前者だけなので、**不統一ではなく意味で分かれている**
2. 「1 行目だけ製品名で他は API 名。抽象度が混ざっている」→ 表の主張は「左の状態が右で何になったか」。
   **揃えると「空いていた穴が埋まった」という主張のほうが消える**

原因は、PDF の画像を 1 回見た印象だけで「不統一」と書いたこと。**表を指摘するなら行数と各行の役割を
数えてから言う**。「不統一」は見た目で言いやすいぶん、意味で分かれている場合に誤りになりやすい。

## 9. C-4 の調査結果 — `touyou/skills` とは manifest の構成が違う

[`touyou/skills`](https://github.com/touyou/skills) は Codex 向けの配布実績があり、README も
`codex plugin marketplace add touyou/skills` を案内している。ただし IntentTodo と構成が違う:

| | `touyou/skills` | IntentTodo |
|---|---|---|
| Codex marketplace 定義 | `.agents/plugins/marketplace.json` | 同じパス・**同形**（+ `authentication: "ON_USE"`） |
| Codex plugin manifest | **`.codex-plugin/plugin.json`** | **直下 `plugin.json`**（Agent Plugins 1.0 / `$schema` 1.0.0 固定） |

- **marketplace 登録の形は同一**なので、「repo を marketplace として追加して 1 プラグインとして出てくる」
  ところまでは実績がある。「仕様通りならいける」という見立ては妥当
- **残る差分は plugin manifest の置き場だけ**。Codex がどちらを解決するかは手元に CLI が無いので確定できない。
  `skills/INSTALL.md` は marketplace 側の 4 パスの first-match は突き止めているが、**manifest 側は未調査**
- ⭐ `touyou/skills` に **`fresh-session-e2e`**（配布物の初回導入 UX を /tmp の空ディレクトリ +
  ゼロコンテキストセッションで E2E 検証する skill）がある。**この用途のために本人が作ったものなので、
  IntentTodo に対して回すのが一番確実**
