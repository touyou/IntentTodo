# 2026-09-25 「スマホで快適な TODO アプリ」の論点をこのアプリに当ててみた

「TODO アプリはスマホで快適にしようとすると実力が出る」という趣旨の投稿（13 個の問いが
並んでいる）を、実装と 1 つずつ突き合わせた記録。**当たっていた 4 件を直し、判断が要る
3 件を issue に出した**。

## 直した 4 件

### 一覧行の `lineLimit` が抜けていた

watch（2）/ ウィジェット（1）/ ライブアクティビティ（2）には入っているのに、iOS と macOS の
`TodoRowView` だけ無かった。単なる抜け。長文タイトル 1 件で行が数画面ぶんに伸びる。3 行にした。

### フィルタ中のドラッグが全体の順序を壊す

`TodoListView` が `onReorder` に渡していたのは `filteredTodos` で、`ReorderDifference.newOrder(from:)`
はその配列の id しか返さない。`TodoService.reorderTodos(orderedIDs:)` は渡された配列の添字を
そのまま `sortIndex` にするので、**見えている分だけに 0..n が振られ、隠れていた todo の index と
衝突する**。

並び替えの有効化条件は `sortOrder == .manual` だけで、リスト / タグ / 検索 / 完了フィルタとは
独立している。なので**単一端末でも**「Work だけ表示して並び替え → 絞り込みを外すと順序が混ざる」
で再現する。端末間（`sortIndex` が絶対位置なので LWW で歯抜けになる）はこの下位の問題で、
今回は触っていない。

`TodoListViewModel.manualOrder(applying:to:)` を足して、隠れていた行は今のスロットに固定した
まま、見えていたスロットだけをドラッグ結果で埋め直してから渡すようにした。

### 完了済みがずっと残る

既定フィルタが `.all` だったので、完了済みが取り消し線のまま永久に積もっていた。`completionDate`
は `.reminders.reminder` スキーマ用に保存していて、完了を書く全経路が更新しているのに、UI からは
一度も読んでいなかった。

既定を `.incomplete` にして、**チェックした直後の行だけ 3 秒残す**形にした。チェックの手応えは
チェックボックスが埋まって取り消し線が入ることだけなので、同じフレームで消すと何が起きたか
残らない。逆に残り続けると「しまわれる」が嘘になる。

実装で引っかかったのは **猶予切れがストアの変化ではない**こと。完了そのものは `@Query` が拾って
再描画するが、3 秒後に行が去るイベントは誰も発火しない。最も早い期限に `.task(id:)` で起床して
`graceNow`（`@State`）を打ち直し、それを `filteredTodos(now:)` に渡す形にした。待っている行が
無ければ id は `nil` なので、何もしていない一覧は何もスケジュールしない。バックグラウンドから
戻って `graceNow` が 1 時間古いような場合も、期限が過去なら `remaining <= 0` でその場で打ち直す。

既定を変えたことで 2 箇所が連動した。どちらも変えなければ**起動直後の見た目が嘘になる**もの:

- `isNarrowed` が `.all` と比べていたので、`.incomplete` が既定になった瞬間に起動するたび
  オプションボタンが `ellipsis.circle.fill`（絞り込み中）になる → `defaultFilter` と比べる
- 空の一覧が `filter` で分岐していたので、新規インストールが todo 0 件で「All Done!
  You've completed all your todos!」と出る → 先に「ストアが空か」で分岐して「No Todos」+
  追加ボタンにする

スクショのフィクスチャも `completionDate = now` を「昨日」に倒した。そのままだと完了済みの
1 件が猶予に入った状態で起動し、1 枚目のスクショには写って 2 枚目には写らない。#158 に
コメントを入れてある。

### iOS の長押しが空振り

行の `contextMenu` が `#if os(macOS)` だけだった。iOS では長押しに何も割り当てが無く、しかも
**手動ソートのときだけ** `.reorderable()` のドラッグに変わる。同じジェスチャが設定次第で
「何も起きない / 並び替え」に化けていた。

macOS と同じ intents をメニューに出し、**手動ソート中だけ iOS では出さない**ようにした。
`contextMenu` は中身が空でも空のメニューを開くので、出し分けは `if` ではなく modifier を
当てるかどうか（`RowMenu`）で決める必要がある。

## インライン編集を追わないと決めた

投稿の中心は「行をその場で編集させるときの確定の仕様が難しい」で、実際このアプリには当たって
いない（編集はシート）。ただし「編集のたびにモーダルは体験が悪い」という指摘自体は当たっていて、
タイトルを直すのに 4 手かかる。

ここで面白いのは、**App Intents 中心設計だとインライン編集の「確定」を置く場所が制約される**
こと。`perform()` を手で呼べない（`@Dependency` がシステム dispatch 経由でしか注入されない）
ので、確定は必ず `Button(intent:)` を押す形になる。`onSubmit` に確定を載せられないので、
「return で確定して次の行へ」は成立しない。キーボードを出したまま確定したいなら
`ToolbarItemGroup(placement: .keyboard)` に `Button(intent:)` を置くしかない。

本人判断で**インライン編集は目指す体験ではない**ことになったので追わない。この制約自体は
登壇で使える形なので記録として残す。
